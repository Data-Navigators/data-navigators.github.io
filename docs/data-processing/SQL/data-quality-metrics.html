SQL Transformations & Data Quality Metrics

Cleaning data is only half the job. A good data analyst also transforms data into analysis-ready shapes and measures how trustworthy the result is. This page shows reusable SQL transformations and the data-quality metrics that accompany them.

Schema note: total_amount (used in the staging examples below) is the same monetary value as quantity * unit_price (used in the modelled examples and the pipeline example). They are two ways of expressing the same order total.

Part 1 — Common SQL transformations​

These are the transformations you will use repeatedly when preparing data for analysis.

1. Standardise text (trim, case, whitespace)​

Inconsistent casing and stray spaces silently break joins and group-bys.

SELECT
    customer_id,
    TRIM(UPPER(customer_name))  AS customer_name,
    TRIM(LOWER(email))           AS email
FROM raw_customers;

2. Handle nulls with sensible defaults​

Replace missing values with a business-meaningful default rather than leaving NULL to propagate.

SELECT
    order_id,
    COALESCE(discount, 0)          AS discount,      -- missing discount = no discount
    COALESCE(region, 'Unknown')    AS region,        -- missing region = unknown
    COALESCE(total_amount, 0)      AS total_amount
FROM raw_orders;

3. Cast and parse types safely​

Convert strings to the correct type, guarding against bad values.

SELECT
    order_id,
    TRY_CAST(order_date AS DATE)   AS order_date,    -- NULL instead of error on bad input
    TRY_CAST(total_amount AS DECIMAL(10,2)) AS total_amount
FROM raw_orders;

TRY_CAST (Snowflake/BigQuery) returns NULL for unparseable values instead of failing the whole query. Use it to surface bad data rather than crash on it.

4. Deduplicate with a window function​

Keep the latest record per entity when a source contains multiple versions.

WITH ranked AS (
    SELECT
        customer_id,
        customer_name,
        email,
        updated_at,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY updated_at DESC
        ) AS rn
    FROM raw_customers
)
SELECT
    customer_id,
    customer_name,
    email,
    updated_at
FROM ranked
WHERE rn = 1;

5. Build a fact table with joins​

Combine transactional rows with dimension tables to produce an analysis-ready fact.

SELECT
    o.order_id,
    o.order_date,
    c.customer_id,
    c.customer_name,
    p.product_id,
    p.category,
    o.quantity,
    o.unit_price,
    o.quantity * o.unit_price AS revenue
FROM orders o
LEFT JOIN customers c ON o.customer_id = c.customer_id
LEFT JOIN products  p ON o.product_id  = p.product_id;

6. Aggregate to a business grain​

Roll up to the level the business actually cares about.

SELECT
    c.region,
    DATE_TRUNC('month', o.order_date) AS order_month,
    SUM(o.quantity * o.unit_price)     AS revenue,
    COUNT(DISTINCT o.order_id)         AS order_count,
    COUNT(DISTINCT o.customer_id)      AS customer_count
FROM orders o
LEFT JOIN customers c ON o.customer_id = c.customer_id
GROUP BY c.region, DATE_TRUNC('month', o.order_date)
ORDER BY c.region, order_month;

Part 2 — Data quality metrics​

Transformations are only trustworthy if you can measure the quality of the data going in and coming out. Data quality is typically assessed along six dimensions:

DimensionQuestion it answers
CompletenessAre required values present?
UniquenessAre there duplicate records?
ValidityDo values conform to expected formats/ranges?
AccuracyDo values match reality?
ConsistencyDo values agree across systems?
TimelinessIs the data fresh enough to use?

1. Completeness — % of missing values per column​

SELECT
    COUNT(*)                                        AS total_rows,
    COUNT(customer_id)                              AS customer_id_filled,
    COUNT(email)                                    AS email_filled,
    ROUND(100.0 * COUNT(customer_id) / COUNT(*), 2)   AS customer_id_completeness_pct,
    ROUND(100.0 * COUNT(email) / COUNT(*), 2)         AS email_completeness_pct
FROM raw_customers;

2. Uniqueness — detect duplicate keys​

SELECT
    customer_id,
    COUNT(*) AS occurrences
FROM raw_customers
GROUP BY customer_id
HAVING COUNT(*) > 1
ORDER BY occurrences DESC;

3. Validity — flag out-of-range or malformed values​

SELECT
    order_id,
    total_amount,
    validity_flag
FROM (
    SELECT
        order_id,
        total_amount,
        CASE
            WHEN total_amount < 0 THEN 'negative_amount'
            WHEN total_amount IS NULL THEN 'missing_amount'
            ELSE 'valid'
        END AS validity_flag
    FROM raw_orders
)
WHERE validity_flag != 'valid';

4. Consistency — find values that disagree across sources​

SELECT
    a.customer_id,
    a.region AS crm_region,
    b.region AS billing_region
FROM crm_customers a
JOIN billing_customers b ON a.customer_id = b.customer_id
WHERE a.region != b.region;

5. Timeliness — how stale is the latest data?​

SELECT
    MAX(load_timestamp)              AS last_load,
    DATEDIFF('hour', MAX(load_timestamp), CURRENT_TIMESTAMP) AS hours_since_load
FROM raw_orders;

6. A combined data-quality summary​

Bring the most important checks into a single, monitorable result set.

WITH checks AS (
    SELECT 'total_rows'            AS metric, COUNT(*)::VARCHAR AS value FROM raw_orders
    UNION ALL
    SELECT 'missing_customer_id',  COUNT(*)::VARCHAR FROM raw_orders WHERE customer_id IS NULL
    UNION ALL
    SELECT 'duplicate_order_ids',  COUNT(*)::VARCHAR
        FROM (SELECT order_id FROM raw_orders GROUP BY order_id HAVING COUNT(*) > 1)
    UNION ALL
    SELECT 'negative_amounts',     COUNT(*)::VARCHAR FROM raw_orders WHERE total_amount < 0
)
SELECT * FROM checks;

Putting it together: a data-quality gate​

A data-quality gate is a rule that blocks a pipeline from proceeding when a metric falls below a threshold. For example:

Rule: proceed only if email_completeness_pct >= 95 AND duplicate_order_ids = 0 AND negative_amounts = 0.

By combining the transformations above with these metrics, you move from "I cleaned the data" to "I cleaned the data and can prove it is trustworthy." That proof — in the form of measurable, reproducible checks — is what a data analyst delivers alongside every report.
